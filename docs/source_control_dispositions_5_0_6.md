## Execution observation boundary

The collector runs actual registered CTest commands with an isolated startup
observer. Source hashes, exact registry/JUnit membership and entry-process
argument/mode observations are independent checks. Python interpreter options
and application arguments are distinct parts of the process contract.

The explicit `calls` mode records called functions and assertion lines. The
`audit_only` mode preserves execution/compilation hashes and actual subprocess
events while leaving the Python trace hook unchanged. Each receipt declares
its mode, and the root identity check requires that exact mode. Audit-only
results are joined with the separately scoped helper-call witnesses.

Only assertion-bearing source and dynamically compiled assertion code need
per-call tracing. Module execution, compilation source hashes and subprocess
arguments are recorded separately. Ordinary recursive data comparisons do not
need millions of profiling callbacks. The observer leaves the C-call profiler
unchanged. Self-tests cover file code, a synthetic filename and a dynamic body
using an existing file's name under ordinary and optimized Python.

The [initial overhead diagnostic](source_control_observer_overhead_5_0_6.md)
records the interrupted first observation. The corrected observer's actual
same-command performance receipt retains unchanged source-validator stdout.
Terminal execution and called-boundary dispositions must be read from their
corresponding receipts; a classification table alone does not sign off SQ02.

Executable source has distinct roles that require distinct dispositions:

- The configuration fixture extracts pure input-producing AST nodes. It checks
  the original bootstrap recipes, scalar cardinalities, thirty selected
  configuration corpora and all 5,080 inputs. Its original collector entry
  bodies remain outside that call path.
- Generated and private-source validators hash-check their recipe files and
  selected ASTs before evaluating them. Function, expression, statement and
  fixture recipes retain explicit result types, cardinalities and complete
  corpus-vector comparisons.
- Admission controls deliberately load preceding comparator or inventory
  implementations to reproduce a known failure. Their current enclosing
  predicates check the expected old and current outcomes. The loaded historical
  counterexample is evidence about the transition, rather than the active
  acceptance implementation.
- The SQL mutation loader checks the complete historical source digest before
  compiling with `optimize=0`. Its ordinary and optimized controller cases are
  retained in the [archive boundary review](executed_import_boundary_review_5_0_6.md#enforced-sql-mutation-archive-boundary).
